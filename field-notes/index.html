Interactive shell / TTY upgrade

For an existing POSIX reverse shell. Local steps below assume an interactive Bash terminal with job control.

1 / REMOTE SHELL

Allocate a PTY

Python 3 + Bash
python3 -c 'import pty; pty.spawn("/bin/bash")'

If Bash is absent, use /bin/sh. Skip this if your connection already uses a PTY (for example, the Python or Socat PTY entry).

Alternative: util-linux script
script -q -c /bin/bash /dev/null

Linux util-linux syntax; BSD/macOS script flags differ.

2 / LOCAL TERMINAL

Background the listener

Press Ctrl + Z. You should return to your local shell. This is a keyboard action, not text to paste into the remote shell.

stty size
printf '%s\n' "$TERM"
jobs -l

Record rows, columns and TERM. Use jobs to identify the suspended listener before foregrounding it.

3 / LOCAL TERMINAL

Raw mode, then foreground

stty raw -echo; fg

Run both parts together in local Bash. If the listener is not the current job, replace fg with its job number, such as fg %2. Press Enter once after it resumes if needed.

4 / REMOTE SHELL

Match the terminal

export TERM=xterm-256color
stty rows 40 columns 120

Replace TERM and the example 40×120 dimensions with the values from step 2. TERM describes capabilities; it does not create a PTY.

5 / LOCAL RECOVERY

Restore input and echo

stty sane

After the remote shell exits, run this in your local terminal. If echo or Enter is broken, press Ctrl+J, type stty sane, then press Ctrl+J again. Use reset afterward if the display is still garbled.

WEB & API

Test relationships,
not just endpoints.

Use controlled accounts and records. Change one dimension at a time so a result has an explanation.

A compact authorization test matrix
ActorObjectActionQuestion
User AA’s recordReadDoes the baseline work?
User BA’s recordReadIs ownership enforced server-side?
User BA’s recordUpdateDoes write authorization differ from read?
User AOther tenant’s recordRead / exportIs the tenant boundary enforced on both paths?
Logged-out userPreviously accessible recordReadDo session expiry and caching preserve the boundary?

Keep the request pair.

  • Save a successful baseline, then one altered request.
  • Record which identity owns the object and which identity sends the request.
  • Compare the response body and server-side state; a 200 alone proves little.
  • Include the smallest controlled record that demonstrates impact.

Follow the state change.

  • Check alternate methods, batch actions and export paths against the same policy.
  • Test a role downgrade with an existing session.
  • Compare UI restrictions with direct API behavior.
  • Separate object access, field access and action permissions in the finding.
03

LINUX PRIVILEGE REVIEW

A permission is
an attack surface.

Read the exact rule before drawing a conclusion. A version number or an interesting binary name is not proof of escalation.

Establish the context.

id
uname -sr
sudo -l
printf '%s\n' "$PATH"

Identify the current user and groups, then inspect allowed sudo commands. Listing privileges may prompt for authentication and can be logged.

Read the whole sudo rule.

Run-as identity
Which user can the command run as? “Allowed” does not always mean root.
Arguments & environment
Are arguments restricted? Which variables survive? Does the program load other files or launch child processes?
Writable dependencies
Check the approved command’s scripts, configuration and parent directories—not just its own mode bits.

Inspect one dependency.

namei -l /path/to/approved-command
stat /path/to/approved-command
getcap /path/to/approved-command

Replace the placeholder with an in-scope path. namei and getcap are Linux utilities and may require installation.

Explain the policy failure.

Record the initial identity, exact permission, dependency involved and resulting identity. Recommend removing the excessive permission or replacing it with a narrowly scoped operation, then retest that operation.

04

ACTIVE DIRECTORY

An edge needs
an explanation.

A useful attack path identifies the principal, permission, affected object and conditions that make the relationship usable.

Before collection

  • Confirm domain naming, DNS resolution and time synchronization.
  • Record collection identity, scope, timestamp and tool version.
  • Keep credential handling separate from shareable command logs.
  • Choose collection methods to match the authorized scope and operational constraints.

Validate the graph.

Principal → object
Is the permission direct or inherited? Does the principal still hold it?
Group → privilege
Check nesting, current membership and the effective access path.
Configuration → impact
Resolve prerequisites and limiting conditions; a graph edge alone is a lead, not a completed exploit.

Preserve the relationship.

Capture source identity, destination object, exact right, inheritance, observed configuration and the minimal verification. A screenshot of the path is useful context; it does not replace the underlying evidence.

Automate the repetition.

Auto AD Recon is a Python wrapper around NetExec for SMB and LDAP enumeration. It supports null sessions, passwords or NTLM hashes, with built-in checks, modules or both. Access depends on the target configuration and the selected checks.

05

REPORTING & RETESTING

Make the finding
easy to verify.

A reproducible finding

  1. Context: affected asset, identity, role and necessary preconditions.
  2. Expectation: the boundary that should hold.
  3. Observation: what changed, with a minimal request pair or transcript.
  4. Impact: demonstrated access, separated from further possible impact.
  5. Remediation: the control that must enforce the intended rule.

A useful retest

Repeat the original case, check the legitimate workflow still works, then test one adjacent path that depends on the same control. Record the build or configuration and date; do not mark a fix complete from a changed status code alone.
